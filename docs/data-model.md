# Module 1 data model and database rules

All domain tables use UUID primary keys and `created_at`. Tenant-owned rows carry an `organization` foreign key; indicator snapshots are global local-cache records. Foreign keys use `PROTECT` for investigation history unless noted; user references in `Feedback` use `SET_NULL`. PostgreSQL constraints are defined in `core.models`, with tenant and audit triggers in migrations `0002`, `0003`, and `0004`.

## Relationship guards

Migration `0002_tenant_integrity` rejects a case whose mailbox belongs to another organization, and rejects artifacts, runs, evidence, actions, feedback, or audit events linked to a case in another organization. Evidence and actions must also reference an analysis run in their own case; evidence artifacts must belong to that case. An existing tenant-owned row cannot change organizations, and artifacts and analysis runs cannot move to another case. The application services validate these relationships before insertion; the triggers remain the database backstop.

## Processing and storage boundaries

`EmailCase` states are queued, processing, analyzed, action_pending, completed, and failed. `AnalysisRun` states are queued, running, succeeded, failed, and cancelled. `ActionExecution` states are proposed, authorized, running, reconciling, succeeded, failed, and skipped. The check constraints validate values and a few timestamp relationships; they do not implement the full workflow transition policy.

`Artifact.file` uses a private filesystem storage class, a random path under organization/case UUIDs, and no public URL. Gmail ingestion stores original MIME only in that private store and records its digest/size as evidence. Migration `0005` adds the enrollment boundary and marks pre-boundary Gmail records historical with visible coverage uncertainty. Migration `0006` adds explicit Gmail failure states, retry timing, analysis leases, and deletion tombstones without deleting prior rows. Neither raw email content nor provider credentials belong in fixtures or logs. A real deployment also needs encryption, retention jobs, and a production HTTPS server.

Migration `0007` adds nullable/defaulted structured evidence columns and the indicator cache tables without rewriting original MIME or existing evidence. New rule evidence is validated in `record_evidence` to require an analysis run, rule ID/version, source field, provenance, and limitations. See [Module 6 detection](module6-detection.md).

Migration `0008` adds opt-in sender and conversation context flags to `Mailbox`, plus `InvestigationRun` and `InvestigationStep`. Each case/policy version has at most one run; each run has unique numbered steps and unique tool-request hashes. State and positive step-number checks constrain the persisted trace. Migration `0009` adds a PostgreSQL trigger requiring an investigation's organization, mailbox, case, and source analysis run to match and keeping those links immutable. See [Module 8 investigation](module8-investigation.md).
